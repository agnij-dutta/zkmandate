# zkmandate: Private Mandates

**ZK isn't for privacy coins. It's for proving your agent followed the rules without revealing the rules.**

An AI agent proves that a payment fits its spending mandate (per-tx cap, cumulative cap,
payee allowlist, expiry) **without revealing the mandate**. The chain stores a Poseidon2
commitment. Escrowed USDC is released only when a valid UltraHonk proof is supplied.

This is the private sibling of [Capline](https://github.com/agnij-dutta/capline). In
Capline, `MandateRegistry` stores `maxPerTx`, `maxCumulative`, `expiry` and the
allowlist root in public storage, so anyone (including competitors) can read an agent's
budget and runway. zkmandate keeps the same semantics and enforcement point
(settlement, not the prompt), and hides the terms.

```
payment 1  $4  -> weather-api  PAID  proof 7872B in 1011ms, verified on-chain, gas 2,502,775
payment 2  $4  -> gpu-rental   PAID  ...
payment 3  $3  -> search-api   PAID  ...
payment 4  $2  -> weather-api  NO PROOF (OVER_CUMULATIVE) the circuit is unsatisfiable, nothing to submit
```

The 4th payment is under the per-tx cap but over the remaining budget. The agent cannot
produce a proof at all, so there is nothing to submit, nothing to front-run and nothing
for a jailbroken model to talk its way around.

## Numbers

6,730 UltraHonk gates · proof in ~0.5 s native / ~1 s pure WASM on an M4 laptop · 28 MB
peak RAM · 7,872-byte proof · ~2.45M gas to verify on-chain. Details and method in
[BENCHMARKS.md](BENCHMARKS.md).

## Quick start

Requires `nargo 1.0.0-beta.19`, `bb 4.0.0-nightly.20260120` (match these: the bb.js and
noir_js versions in `sdk/package.json` are pinned to them), Foundry, Node 22.

```bash
git submodule update --init
(cd sdk && npm install)
./scripts/build.sh        # compile circuit, write vk, generate Solidity verifier, forge build
./scripts/test-all.sh     # nargo test + forge test + SDK tests
cd sdk && npm run demo    # spins up anvil, deploys, agent pays 3x privately, 4th has no proof
                          # BACKEND=native npm run demo  (native bb, about 2x faster)
```

## SDK

```ts
import { createMandate, initialState, contextFor, proveMandatePayment, MandateViolation, toHex32 } from "zkmandate";

// Principal: write the mandate. Only `commitment` and the initial head go on-chain.
const mandate = await createMandate({
  maxPerTx: 5_000_000n, totalCap: 12_000_000n,          // USDC, 6 decimals
  notAfter: BigInt(Math.floor(Date.now() / 1000) + 7 * 86400),
  payees: [WEATHER_API, GPU_RENTAL, SEARCH_API],
});
let state = initialState(mandate);
await registry.createMandate(toHex32(mandate.commitment), toHex32(state.head), agentAddress);

// Agent: prove, pay, advance.
const context = contextFor(chainId, registryAddress, mandate.commitment);
try {
  const p = await proveMandatePayment(mandate, state, { amount: 4_000_000n, payee: WEATHER_API, validUntil, context });
  await registry.pay(p.args.mandate, p.args.payee, p.args.amount, p.args.validUntil, p.args.newHead, p.args.proof);
  state = p.newState;
} catch (e) {
  if (e instanceof MandateViolation) console.log("refused:", e.reason); // OVER_PER_TX, OVER_CUMULATIVE, EXPIRED, PAYEE_NOT_ALLOWED, ...
}
```

`ZkMandateProver.create({ backend })` picks the bb.js backend: `Wasm` (default, fully
in-process, runs anywhere) or `NativeUnixSocket` (about 2x faster, needs the native bb).

## Design

### The statement

Public inputs (in this order): `mandate`, `old_state`, `new_state`, `amount`, `payee`,
`valid_until`, `context`. Private: `max_per_tx`, `total_cap`, `not_after`,
`allowlist_root`, `salt`, `spent`, `state_salt`, `payee_index`, `payee_path[8]`.

The circuit proves:

1. `mandate == H(1, maxPerTx, totalCap, notAfter, allowlistRoot, salt)`
2. `old_state == H(4, mandate, spent, stateSalt)`
3. `0 < amount <= maxPerTx`
4. `spent + amount <= totalCap` (in u128, no wraparound)
5. `valid_until <= notAfter`
6. `H(2, payee)` is a leaf of the depth-8 Merkle tree with root `allowlistRoot`
7. `new_state == H(4, mandate, spent + amount, H(5, salt, old_state, context))`

`H` is Poseidon2 over BN254 (cheapest hash in UltraHonk), with a distinct domain tag per
role so no preimage can be reinterpreted as another kind of value.

### Cumulative caps without a public counter: the state chain

The registry stores one `head` per mandate: a hiding commitment to `spent`. Each proof
opens the current head privately and outputs the successor head with `spent + amount`.
The contract only accepts a proof whose `old_state` equals its stored head, then moves
the head forward. Consequences:

* **Replay protection for free.** A replayed proof refers to a stale head and cannot
  verify. No nullifier set, no growing storage: one 32-byte slot per mandate.
* **No forks.** The next salt is derived in-circuit from the mandate secret, the old head
  and the context, so a given head has exactly one valid successor for a given amount.
  The agent cannot under-report spend (test `test_cannot_under_report_new_spent`) or
  reset it (`test_cannot_lie_about_spent`) without breaking Poseidon2.
* **Recoverable state.** Because salts are derived, not random, an agent that loses its
  local state can rebuild it from the mandate secret plus the public `Paid` events.
* **Sequential per mandate.** Payments on one mandate are strictly ordered. An agent can
  pre-compute proof N+1 against the expected head before N lands; if N fails, N+1 is void.

### Why the payee is public

The payee is a public input (the raw address), not a commitment. On a transparent EVM
the escrow has to `transfer(payee, amount)`, so the payee is visible in the token
transfer no matter what the proof says. Making it public also binds the proof to the
recipient: a relayer, front-runner or compromised RPC cannot take a valid proof and
redirect the funds (`test_RevertWhen_WrongPayee`). What stays hidden is the *allowlist*:
the other vendors and how many there are (the tree is always depth 8 with zero padding).
Hiding the payee too needs a shielded token, see TODOs.

### Why `valid_until` instead of `now`

The prover cannot know the block timestamp of the block that will include its tx. So
the proof states `valid_until <= notAfter` and the contract checks
`block.timestamp <= valid_until`. Together: payment time `<= notAfter`, exactly, with no
skew window. The agent picks a short `valid_until` (for example now + 10 minutes) so it
leaks only "the mandate does not expire in the next 10 minutes".

### Domain binding

`context = keccak256(chainid, registry, mandate) >> 8` is a public input the contract
computes itself and the circuit folds into the next salt. A proof for one chain or one
registry deployment is useless on any other (`test_RevertWhen_ProofReplayedOnOtherRegistry`).

### Registry

`PrivateMandateRegistry.sol`:

* `deposit` / `withdraw`: **pooled escrow per principal**, so a deposit does not reveal
  an upper bound on any single mandate's cap.
* `createMandate(commitment, initialHead, agent)`, `revoke(commitment)` (principal only).
* `pay(mandate, payee, amount, validUntil, newHead, proof)`: only the registered agent
  may submit (a leaked mandate secret alone cannot spend), rejects expired / revoked /
  non-canonical inputs, verifies the proof against the stored head, advances the head,
  then transfers. Any verifier revert is normalized to `InvalidProof`.

## Security notes: what is and isn't hidden

**Hidden from everyone except the principal and the agent**

* `maxPerTx`, `totalCap`, `notAfter`
* the payee allowlist: members not yet paid, and its size (up to 256)
* the remaining budget (because `totalCap` is hidden)

**Public, and why**

* Each payment's **payee and amount**: they are a USDC transfer on a transparent chain.
  Consequence: `spentSoFar` is reconstructable by summing `Paid` events for a mandate.
  The state commitment chain is what lets the circuit enforce the cumulative cap without
  the contract storing it; it hides `spent` only once amounts are hidden too (shielded
  token or batched settlement).
* **Lower bounds** leak naturally: the largest observed payment bounds `maxPerTx` from
  below, total paid bounds `totalCap` from below, each `valid_until` bounds `notAfter`
  from below, and every paid vendor is revealed as an allowlist member.
* **Linkability**: all payments of a mandate share its commitment, and principal and
  agent addresses are public. The principal's pooled escrow balance is public.
* **Revocation** is public (it is an on-chain call).

**Trust and soundness assumptions**

* The salt must be high entropy (the SDK uses 248 random bits). With a guessable salt,
  low-entropy caps like "$5 / $20" can be brute-forced from the commitment.
* The principal is trusted to compute the initial head (spent = 0) correctly; getting
  it wrong only bricks their own mandate.
* The agent holds the mandate opening. Agent key + opening can spend up to the mandate,
  which is exactly Capline's guarantee: a jailbroken or key-compromised agent still
  cannot exceed the caps. Leaking the opening reveals the terms to whoever gets it.
* Proofs must use the ZK flavor (`-t evm` / `verifierTarget: "evm"`). The non-ZK flavor
  is not guaranteed to hide the witness.
* UltraHonk uses KZG with the universal Aztec Ignition SRS: no circuit-specific trusted
  setup, but the usual powers-of-tau trust assumption.
* **Nothing here is audited.** Noir is `1.0.0-beta.19`, bb is a 4.0.0 nightly, and the
  Solidity verifier is generated by that nightly. The circuit uses
  `noir-lang/poseidon v0.2.6` (the last tag compatible with beta.19) and only its
  fixed-length `Poseidon2::hash`; v0.4.0 fixed a bug in the streaming `Hasher` API,
  which this circuit does not use. Hashes are cross-checked between Noir and bb.js in
  the SDK tests. Testnet / demo use only.

## Solana path (not built)

Barretenberg has no Solana verifier target, so a Solana version needs one of:

1. **Groth16 via gnark.** Port the circuit to gnark (or compile Noir to a gnark/R1CS
   backend, as the community "sunspot"-style toolchains do) and verify with the
   `alt_bn128` syscalls through `groth16-solana` (Light Protocol). Proof is 256 bytes and
   verification is roughly 200k compute units, cheaper than the EVM path by a lot. Cost:
   a second circuit implementation plus a per-circuit trusted setup.
2. **Keep UltraHonk, verify off-chain, attest on-chain.** A small verifier network
   or TEE checks the proof and posts a signed attestation that the Capline Solana program
   checks with the ed25519 precompile. Cheap to build, adds a trust assumption.
3. **Native UltraHonk verifier program.** Pairings via `alt_bn128` syscalls are
   available, but sumcheck + Shplemini in BPF would very likely blow the 1.4M CU budget
   per transaction and need to be split across several transactions. Research project.

Option 1 is the realistic one; Capline's Solana program would swap its public
`max_per_tx` / `total_cap` / `merchants` fields for `commitment` + `head`, exactly like
the EVM registry here.

## TODOs

* Hide amounts and payees: settle through a shielded pool (or a private-transfer token)
  so `spent` is genuinely hidden, then the state chain carries its full weight.
* Batch / aggregate: recursively fold N payments into one proof (bb `noir-recursive`
  target) to amortize the ~2.4M gas verify.
* Bind the mandate to Capline's AP2 Intent Mandate hash and to an ERC-8004 agent identity

  check the mandate is authorized without trusting the registry caller.
