# Security policy

zkmandate moves tokens on the strength of zero-knowledge proofs. It has **not been
audited**. It is built on pre-release toolchains (Noir `1.0.0-beta.19`, Barretenberg
`4.0.0-nightly.20260120`). Use it on testnets and local chains only.

## Reporting a vulnerability

Please report privately through GitHub's private vulnerability reporting:
**Security tab -> Report a vulnerability** on
<https://github.com/agnij-dutta/zkmandate>. Do not open a public issue for a soundness
or fund-loss bug.

Include the affected component (circuit, registry, SDK), the commit, and a reproduction:
a failing `nargo test`, `forge test` or SDK test is ideal. Expect a first reply within a
few days.

## In scope

- `circuits/src/main.nr`: soundness (a proof for a payment that breaks the mandate),
  under-constrained witnesses, hash domain confusion, Merkle path handling.
- `contracts/src/PrivateMandateRegistry.sol`: escrow accounting, access control, replay,
  public input binding, reentrancy.
- `sdk/src`: anything that makes the SDK produce or accept a proof that differs from what
  the circuit and registry check, or that weakens the hiding of the terms (for example
  salt handling).
- The pipeline in `scripts/build.sh` that regenerates the verifier from the circuit.

`contracts/src/HonkVerifier.sol` is generated by `bb write_solidity_verifier`. Bugs in it
belong upstream at <https://github.com/AztecProtocol/aztec-packages>, but tell us too.

## Review status

An internal review (2026-10-04) covered the items below. Fixed issues have regression
tests; the test name is listed.

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | Medium | Mandates were keyed by commitment alone. Anyone could copy a pending `createMandate` commitment from the mempool and register it first, blocking the principal forever (`MandateExists`), once per attempt. | Fixed: storage key is `keccak(principal, commitment)` and the proof context binds the principal. `test_FrontRunCreateCannotSquat`, `test_CopiedCommitmentIsIndependent` |
| 2 | Low | `deposit` credited the requested amount, not the amount received. With a fee-on-transfer token the pooled escrow becomes insolvent for the last withdrawer. | Fixed: balance-delta accounting. `test_FeeOnTransferCreditsReceivedAmount` |
| 3 | Low | Token calls required a `bool` return, so USDT-style tokens could not be used, and there was no reentrancy guard (needed once deposits use balance deltas). | Fixed: tolerant token call plus `nonReentrant`. `test_NoReturnValueTokenWorks`, `test_RevertWhen_TokenReturnsFalse`, `test_ReentrantDepositIsBlocked`, `test_ReentrantWithdrawIsBlocked` |
| 4 | Low | The SDK accepted any caller-supplied salt, including tiny ones, although the hiding of the terms rests entirely on the salt. | Fixed: salts below 2^128 are rejected. SDK test "guessable caller-supplied salts are rejected" |
| 5 | Low | The committed SDK circuit artifact contained `debug_symbols` and a `file_map` with absolute local paths and source copies. | Fixed: `build.sh` keeps only ABI and bytecode |
| 6 | Info | Constructor accepted verifier/token addresses without code (a call to an empty address succeeds). | Fixed: `test_RevertWhen_ConstructedWithoutCode` |

Checked and found sound (with tests guarding them):

- **Range checks.** Every integer input is range constrained in ACIR (`amount`,
  `valid_until`, `max_per_tx`, `total_cap`, `not_after`, `spent` at 64 bits,
  `payee_index` at 32 bits; check with `nargo compile --print-acir`). The cumulative sum
  is computed in `u128`, so it cannot wrap (`test_sum_cannot_wrap_at_u64_max`), and an
  amount of `p - 1` cannot be witnessed (SDK test).
- **Merkle path.** `payee_index < 256` is asserted, so index 256 cannot alias index 0
  (`test_index_alias_rejected`). Leaves are `H(2, payee)` and nodes `H(3, l, r)` with
  different tags and sponge lengths; an empty slot or a leaf value is not a payee
  (`test_empty_slot_is_not_a_payee`, `test_leaf_value_is_not_a_payee`).
- **State chain.** The registry only accepts a proof against its stored head, so replays
  and out-of-order proofs fail (`test_RevertWhen_ReplayedProof`, `test_RevertWhen_OutOfOrder`).
  The successor salt is derived in-circuit, and the new head must commit to
  `spent + amount` (`test_cannot_under_report_new_spent`).
- **Canonical inputs.** The verifier reduces public inputs mod p; the registry rejects
  non-canonical commitments and heads (`test_RevertWhen_NonCanonicalNewHead`).
- **Public input order** is identical in `main`, the registry and the SDK
  (`test_PublicInputOrderMatchesCircuit`, SDK test "valid payment").
- **Access control.** Only the registered agent may `pay`; only the principal can reach
  its own mandate for `revoke`; escrow is per principal (`test_EscrowIsPerPrincipal`).

## Known limitations and non-goals

These are design properties, not bugs. They are also listed in the README.

- **Amounts and payees are public.** Every payment is a visible token transfer, so
  `spent` is the sum of a mandate's `Paid` events. The state chain enforces the cap but
  does not hide spend until amounts are shielded.
- **Lower bounds leak.** The largest payment bounds `maxPerTx`, total paid bounds
  `totalCap`, each `validUntil` bounds `notAfter`, every paid vendor is an allowlist member.
- **The salt is the only thing hiding the terms.** Caps and expiries are low entropy. A
  leaked or guessable salt lets anyone who also guesses the allowlist brute-force the
  terms from the commitment. The salt is shared by principal and agent; leaking either
  side's copy reveals the terms (but does not let anyone spend: only the agent address can).
- **The principal can withdraw at any time**, including just before an agent's payment
  lands. Payees who deliver before payment settles are trusting the principal.
- **Revocation can be raced.** An agent that sees `revoke` in the mempool can land a valid
  payment first.
- **The principal computes the initial head.** A wrong head bricks only its own mandate.
- **One budget per registration.** Registering the same commitment on two registries or
  chains gives the agent the full cap on each. Use a fresh salt per registration.
- **`payee` is not range checked in the circuit.** The registry always supplies a
  160-bit address. An off-chain verifier must do the same.
- **ZK flavor required.** Proofs must use `-t evm` / `verifierTarget: "evm"` (ZK). The
  non-ZK flavor may leak witness data.
- **Trusted setup.** UltraHonk uses KZG over the Aztec Ignition SRS.
- **Toolchain.** Noir beta, bb nightly, and a generated verifier that has not been audited
  for this release. `noir-lang/poseidon v0.2.6` is used only through fixed-length
  `Poseidon2::hash`; the streaming `Hasher` bug fixed in v0.4.0 does not apply.
- **SDK proving** temporarily replaces `console.log` while bb.js generates a proof, to
  silence a log line. Concurrent code that logs during that window loses its output.
